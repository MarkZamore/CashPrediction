# Настоящая визуальная проверка S3

Владелец этого дополнения меняет только VisualParityTest и check/visual.
Hotkey-тесты, launcher, pipeline, браузер, core и клиенты не изменяются.
Ни одного модельного PNG, модельного дампа или золотого файла здесь нет.

Последний аудит и актуальные пробелы приведены в заключительном разделе.
Предыдущие разделы с датами сохраняют историю опытов; прежние ошибки Shot
и отсутствие измерений не означают, что соответствующий код всё ещё отсутствует.

## Явный запуск

Реальный тест требует одновременно `-Dparity.visual=true` и
`-Dparity.realClients=true`. Без первого флага обычная регрессия не запускает
окна и браузер. Если visual запрошен, но realClients отсутствует, тест падает,
а не пропускается. Выбор клиентов использует существующий `parity.clients`;
неизвестные клиенты и пустая матрица отклоняются.

```powershell
mvn -o -B -Pui-tests -pl ui-parity -am test '-Dtest=VisualParityTest,VisualRegressionTest' '-Dsurefire.failIfNoSpecifiedTests=false' '-Dparity.visual=true' '-Dparity.realClients=true' '-Dparity.clients=fx,swing,web'
```

Команда предназначена основному владельцу общей сборки после актуального
package клиентов. Launcher использует упакованные jar, а не target/classes;
сама фаза test эти jar не обновляет. Другие агенты общую Maven-сборку не
запускают. Для ручного изолированного запуска JUnit Console используются
локальный JDK 25, замороженные CoreClasses и отдельная папка тестовых классов.
Выход `parity.build.directory` также должен быть уникальным.

## Ограниченные контрольные точки

По умолчанию проверяются четыре первые точки: s02/table, s03/chart,
s05/settings, s08/delete-rule. Каждая запускается отдельным процессом
для каждого выбранного клиента. `parity.visual.scenarios=s02,s03` позволяет
ограничить диагностический повтор сценариями; неизвестный префикс падает.
`parity.visual.checkpoints=all` явно включает каждый dump четырёх сценариев.
Это более долгий запуск; он не выполняется по умолчанию.

VisualPlan берёт исходный сценарий через SelfTestScript.load. Сохраняется
каждая команда до выбранного dump включительно. Добавляются только
`size 1200 800` в начале и `shot <тот же шаг>` после dump. Никакие действия
не заменяются намерением контроллера. Внешний `.cps` принимается штатным
парсером и передаётся существующим --selftest. Today также сохраняется:
неподдерживаемый Today в web будет видимым FAIL, а не скрытой заменой шага.

После завершения журнал обязан иметь ровно по одному OK для каждой строки
и единственный финальный SELFTEST DONE. FAIL, пропуски, дубликаты,
перестановки, неподдерживаемый shot и неправильный текст всегда дают ошибку.
Даже после такой ошибки читаются существующие фактические файлы, чтобы
отчёт показывал реальные свидетельства сбоя. Отсутствующий PNG не рисуется
в стенде и не заменяется пустой или модельной картинкой.

## Изоляция и блокировки Windows

Каждый запуск использует UUID папки и узел
ru/cashprediction/selftest/UUID, --today 2026-09-13 и --ui core.
Переиспользуются ScenarioFixtures, ClientLauncher и WebScenarioSession.
Деревья JVM/Edge закрываются через существующие AutoCloseable API.
Узел удаляется в finally даже после ошибки; реальные session/fx и
session/swing сравниваются с исходным снимком. Ошибка уборки остаётся
ошибкой опыта.

VisualTargets сначала копирует весь разрешённый ClientTarget.modulePath
в run/module-snapshot, включая core, клиент и OpenJFX. Сравниваются байты
источника и копии, проверяется ZIP и наличие module-info.class. Изменение
архива при копировании - ошибка. JVM получает только копии; root jar
и ~/.m2/core не остаются открытыми из-за живого клиентского процесса.
Основной владелец может продолжать упаковку после короткого копирования.

Клиенты выполняются последовательно: Swing Robot должен снимать своё
главное окно и настоящие модальные окна, а не окно другой параллельной
пробы. Все артефакты остаются для диагностики; общие targets не изменяются.

## Что проверяется в изображении и дампе

- Подпись PNG, возможность декодирования, ровно 1200×800 пикселей.
- Дамп имеет тот же viewport 1200×800. Никакого изменения размера,
  обрезки рамки или пересчёта координат под подходящий результат нет.
- Пиксели непрозрачны; пустое/одноцветное изображение не является
  свидетельством реальных виджетов. Разнообразие цветов само по себе
  не доказывает происхождение; его обеспечивает настоящий путь shot.
- Web дополнительно проверяет innerWidth=1200, innerHeight=800 и
  devicePixelRatio=1 через существующий Runtime.evaluate. Desktop
  использует штатные flags uiScale=1 launcher и соответствие PNG/viewport.
  Физический DPI монитора не угадывается из отсутствующих метаданных.
- Все пять основных рамок должны существовать, быть конечными,
  положительными и полностью внутри снимка. Тулбар 36px, статус 24px,
  нижний край статуса 800px проверяются с допуском 4px.
- Цветовые пробы отступа тулбара, сводки и статуса сравниваются с
  ColorToken.BG_WINDOW, а фиксированная проба карточки с BG_CARD.
  CIE76 ΔE должен быть строго меньше 6. Проба - заранее фиксированная
  область 2×2 в отступе, а измеряется её центр. Стенд не ищет пиксель
  подходящего цвета и не считает центральный текст карточки фоном.
- Между выбранными настоящими клиентами рамки регионов, карточек и
  видимых элементов тулбара сравниваются по четырём компонентам ±4px.
  Все рамки читаются в объявленных контрактом UiDump.Box координатах
  содержимого окна. Клиентский дамп с относительными координатами панели
  должен быть исправлен владельцем клиента, иначе сравнение даст ошибку.
- Позиции кнопок форм/сообщений сравниваются по идентичности и x ±4px.
  Для форм и alert всех клиентов x уже относится к содержимому собственного
  окна; DOM-дампер сам вычитает origin. Повторного вычитания в стенде нет.
  Отсутствие отдельного origin alert в схеме не является ошибкой. Пропуск кнопки и расхождение x
  остаются ошибками строгого попарного сравнения.

При одном выбранном клиенте отчёт явно сообщает, что попарная проверка
не запрошена. Собственные проверки viewport, рамок, размеров и цветов
всё равно выполняются. Выбор одного клиента не называется паритетом трёх.

## Отсутствующие измерения не подменяются числами модели

UiDump schema 1 содержит тексты колонок, но не их рамки, и не содержит
текстовых baseline. Чтобы полноценно закрыть требования §6.3 и §9,
дамп настоящего клиента должен добавить в открытый frame.regions:

- `table.column.<stableId>` - рамку каждого реально видимого заголовка;
- `toolbar.baseline` и `status.baseline` - реальную текстовую базовую линию
  в виде Box(x, y, width, 1), в координатах содержимого окна.

Сериализованный самотест округляет геометрию к двум пикселям через
`DumpNormalizer`: высота этой линии становится 2. `VisualImages` принимает
только исходную высоту 1 или её нормализованное представление 2; высота 3
и выход за рамку владельца остаются ошибками. Допуски положения не меняются.
`VisualRegressionTest.acceptsNormalizedBaselineWithoutRelaxingItsPosition`
проверяет оба представления и отрицательный случай.

Так не требуется изменение record-схемы ядра. Все колонки s02/table
обязаны иметь рамки, число проверяется по table.columns. Колонки
сравниваются ±4px, baseline ±3px. Пока рамок нет, тест возвращает
Missing real region / Missing real table.column, а не зелёный результат.
Для alert используется согласованный content-local x кнопок; отдельного
требования origin для web-alert больше нет. Это требования к клиентским дамперам, не разрешение этому агенту
изменять клиент или core.

## Минимальный недостающий путь Web Shot для main

Существующий CdpTestApi.screenshot уже возвращает настоящий
Page.captureScreenshot. UiTestDriver.screenshot проверяет PNG 1200×800.
На момент фактической пробы TestApiBridge вызывал execute для SelfTestCommand.Shot,
который отсутствует в supported страницы, а серверный WebSelfTestBridge
обрабатывает только /api/test/dump и /api/test/result.

Минимальное согласованное расширение других владельцев:

1. TestApiBridge распознаёт Shot аналогично Dump, ждёт idle и вызывает
   driver.screenshot(shot.step()), а не execute(Shot).
2. Закрытый Sender.http разрешает POST /api/test/shot с телом
   `{n, png: Base64}` настоящего PNG. Прежняя авторизация X-Token, origin и запрет
   перенаправлений сохраняются.
3. Сервер принимает только текущий ожидаемый Shot, один раз. Имя файла
   берётся из проверенного сценария, не из произвольного клиентского пути.
   PNG проверяется на подпись, декодирование и 1200×800; задаётся
   ограничение тела запроса. Файл записывается в selftestOut/script.name/
   shot.step.png.
4. OK шага Shot без принятого PNG отклоняется, как сейчас Dump без дампа.
   Ошибка снимка даёт FAIL, ошибка HTTP выходит наружу.

Этот sidecar не обходит отсутствующий маршрут записью браузерной картинки
за спиной сервера. При отсутствии PNG ошибка и нужное минимальное API
записываются в независимый отчёт. Main может реализовать расширение
в принадлежащих ему файлах; тест после этого использует тот же collector.

## Отчёт и регрессионные проверки

Отчёт находится в parity.build.directory/parity/visual-UUID/report.html.
Он не читает goldens: только actual PNG, actual dump, журнал и измерения.
Для каждой точки снимки стоят рядом; первые два доступных снимка можно
наложить и менять прозрачность. Отсутствующий PNG обозначен текстом.
Ссылки ведут к оригинальным файлам и каталогу сценария/журналов.
Ошибки безопасно экранируются в HTML и не могут стать исполняемым кодом.

Исходные syntheticPngColors и positionsHaveFiniteInclusiveTolerance
сохранены. Новые unit-тесты портят фиксированный пиксель, сдвигают
геометрию за 4px, baseline за 3px, удаляют измерения, меняют viewport,
делают PNG прозрачным/одноцветным, портят формат и журнал Shot.
Отдельно проверяются обе gates, сохранность исходных сценарных команд,
отсутствие fake PNG в отчёте и копирование jar перед запуском.
Такие синтетические данные используются только в самопроверках,
никогда в реальной визуальной матрице.
