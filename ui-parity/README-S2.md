# Стенд S2

Актуальное подключение настоящих клиентов описано в [README-S3.md](README-S3.md).
Ниже сохранён отчёт о состоянии S2; ограничение UnsupportedOperationException
для web-сборщика снято в S3, подключение рендереров требует нового handshake.

Все новые классы являются тестовой инфраструктурой. Рендереры S3 ещё не подключены;
успешная проверка этого модуля не доказывает паритет настоящих клиентов.
Изменения ограничены `ui-parity/**`. Сценарии, golden и allowed-diffs принадлежат ядру.

## Проверка без Maven

Из корня репозитория в PowerShell:

```powershell
.\ui-parity\Verify-Infrastructure.ps1
```

Скрипт компилирует текущее ядро (включая module-info для модульного запуска фиктивных JVM)
и все тестовые классы стенда в новой папке `ui-parity/target/parity/compile-<uuid>`.
Запускаются `*Test` и `ParityPipelineIT`; остальные IT с настоящими окнами и браузером
в этот изолированный прогон не входят. Полная матрица реальных клиентов пока явно выключена.
Скрипт содержит точные команды javac и JUnit Console, использует установленный JDK 25
и уже имеющийся JUnit Console 1.14.4. Maven, Node и новые зависимости не используются.

## Сравнение

`ParityPipeline.run` собирает каждый сценарий для каждого выбранного клиента, проверяет
schema/client/scenario/step, требует непустой каталог, сравнивает состав шагов и содержимое
с golden, затем сравнивает клиентов попарно (геометрический допуск 4 px).
`DumpDiff` и `AllowedDiffs` вызываются из ядра, без своей реализации JSON pointers или списка исключений.
Полная матрица требует использования каждой записи allowed-diffs. Частичный прогон явно
пишет в отчёт оставшиеся непроверенными записи; он не подтверждает полный аудит исключений.

`DumpTrees.normalized` нормализует через ядро и требует новый additive API
`DumpNormalizer.comparisonTree(UiDump, Path, String)`. Только ядро решает адресацию списков
по id и сохранение порядка. Стенд исключает только client и classCensus: происхождение
проверяется до сравнения, а реальная перепись FX проверяется отдельно. Wire JSON не меняется.
Синтетические тесты тоже используют этот API ядра, без запасной реализации канонизации.

`ParityPipelineIT` собирает jar фиктивного main, запускает три отдельные JVM через
`ClientLauncher`, копирует тестовый golden и мутирует счётчик web. Проверяются ошибки
golden/web и pairwise, HTML pointer, успешный неизменённый шаг. Эти дампы синтетические.

Выходные данные лежат под `ui-parity/target/parity/<client>/<scenario>/run-<uuid>`.
Новый каталог запуска исключает чтение старых дампов. `ScenarioCollector` требует
`SELFTEST DONE`, отклоняет `SELFTEST ... FAIL`, закрывает дерево процессов и удаляет
только собственный selftest-узел; слепок настоящего session сравнивается до/после.
HTML содержит экранированные указатели и значения, ошибки запуска и чтения.
Кроме `report.html` сохраняется `report-<clients>.html`, чтобы разные наборы клиентов
имели самостоятельные отчёты при параллельном запуске.

## Подключение S3

`UiTestDriver.TestApi` является портом тестового рендерера: точный набор поддерживаемых
классов `SelfTestCommand`, исполнение через виджеты, awaitIdle с учётом debounce,
дамп реальных виджетов и полноценный PNG 1200x800. Необъявленная операция падает.
Дамп с client=model либо другой идентичностью отклоняется. Ошибки не переводятся в успех.

Для браузера `CdpTestApi` использует существующий JDK `CdpClient`, включая awaitPromise
и `Page.captureScreenshot`. Тестовый порт страницы (предлагаемая точка подключения S3,
ещё не реализована в web) имеет вид:

```text
window.cpParityTestApi.supported = ["Sample", "Menu", ...]
execute({kind: "Menu", args: <UiJson tree команды>}) -> Promise<{ok: true}>
awaitIdle({timeoutMs: 5000}) -> Promise<{ok: true}>
dump({step: "sample"}) -> Promise<{ok: true, value: <UiDump wire tree>}>
```

Порт доступен только в режиме `--test-api`. Отсутствие порта, метода, явного `ok:true`
или ошибка Promise дают ошибку. Он обязан отправлять реальные события DOM; методы ядра
не могут служить обходным путём. Этот hook не меняет четыре маршрута рабочего UI API.

`TestApiBridge.accept` принимает один новый эффект `{type:"test.step", n, command}`,
разбирает command существующим парсером ядра, исполняет через UiTestDriver и отвечает
`POST /api/test/result` телом `{n,ok,message}`. Для dump сначала отправляет
`POST /api/test/dump` тело `{n,dump:<wire tree>}`. Повторные/неупорядоченные номера
отклоняются до исполнения. Транспортная ошибка выходит наружу. JDK HTTP канал допускает
только loopback HTTP и эти два маршрута, без перенаправлений. Формы тестовых payload
нужно согласовать при подключении WebSelfTestBridge S3; production протокол ядра не изменён.
Команды раннера, для которых мост не имеет реализации, возвращают FAIL.

Сборщик FX/Swing готов к их `--ui core --selftest`; web пока явно возвращает
UnsupportedOperationException: подключение страницы, получение адреса из запуска сервера
и доставка test.step принадлежат этапу S3. Подмена серверных моделей вместо страницы запрещена.

После подключения S3 ведущий запускает профиль последовательно:

```text
mvn -B -o -Pui-tests -pl ui-parity -am verify -Dparity.realClients=true -Dparity.clients=fx,swing,web
mvn -B -o -Pui-tests -pl ui-parity -am verify -Dparity.realClients=true -Dparity.clients=fx -Dparity.scenarios=s02,s05
```

До подключения рендереров `ParityTest` содержит явный JUnit assumption с причиной S2.
При явном включении отсутствие golden/API/клиента является ошибкой, не пропуском.

`HotkeyParityTest.exactlyOnce` проверяет единственное изменение нужного счётчика;
`ClassUsageTest.census` требует реальные положительные счётчики ожидаемых классов;
`VisualChecks` проверяет CIE76 ΔE < 6 в центре региона и координаты с допуском 4/3 px.
Их тесты синтетические. Полный проход hotkey bindings (включая disabled hints),
перепись 23 классов, source mapping comments и настоящие снимки/overlay ещё требуют S3/S4.
