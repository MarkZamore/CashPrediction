# Протокол тихого обновления CashPrediction

Этот документ фиксирует контракт тихого обновления в составе S5. Отдельный этап S7 объединён с S5 по решению пользователя; исторические имена S7 файлов и проверок сохраняются как технические идентификаторы. За основу взят обновлятор LANMinecraft: один запрос при запуске, фоновая подготовка, не более двух дельт, полный пакет как запасной путь, установка внешним помощником после завершения приложения и восстановление после прерванной установки. Полное соответствие требованиям также входит в S5; после него выполняется независимая финальная проверка S6.

## 1. Границы

- Обновление доступно только релизным Windows-сборкам, у которых `AppInfo.release() > 0` и задан SHA коммита.
- JavaFX, Swing и Web используют один сервис из `core`; в клиентах остаются только одинаковые вызовы запуска и завершения жизненного цикла.
- Проверка выполняется один раз за процесс после появления основного интерфейса. Периодического таймера, ручной команды, индикатора и сообщений интерфейса нет.
- Сетевые и установочные ошибки не препятствуют работе текущей версии.
- Служебные файлы существуют только в `CashMemory/Updates`. Планы, снимки и другие пользовательские данные установщик не изменяет.

## 2. Публикуемые файлы

Релиз `latest` содержит:

- `CashPrediction-portable.zip` - полный запасной пакет;
- `CashPrediction.cpdelta` - дельта от последней сохранённой базы;
- `CashPrediction.from-<номер>.cpdelta` - дельта от второй сохранённой базы, если она есть;
- `release.json` - прежнее описание релиза для человека и внешних средств;
- `update.json` - атомарный указатель, который загрузчик публикует последним.

Две предыдущие успешные базы хранятся в релизах с тегами `update-base-<номер>`. Более старые базы удаляются только после успешной публикации нового `update.json`.

## 3. Манифест update.json

Схема 2 содержит:

- `schemaVersion`, `releaseNumber`, `commitSha`, `version`, `publishedAtUtc`;
- `assetName`, `sha256`, `sizeBytes` полного ZIP;
- `treeSha256` целевого дерева;
- отсортированный `files`: относительный путь с `/`, размер, SHA-256 и `readOnly`;
- до двух `deltaPatches`: `algorithm`, `algorithmVersion`, базовые номер, SHA коммита и хеш дерева, имя, SHA-256 и размер патча.

Алгоритм называется `cashprediction-tree-delta`, версия равна 1. Неизвестная схема или версия алгоритма отклоняется. Обновление применяется только при большем номере релиза; отличающийся SHA с тем же или меньшим номером не вызывает откат.

Управляемое дерево включает три `.exe`, каталоги `app` и `runtime`. `CashMemory` в него не входит. Хеш дерева вычисляется по отсортированным UTF-8 путям, признаку `readOnly`, размеру и SHA-256 содержимого, поэтому не зависит от временных меток ZIP.

## 4. Формат .cpdelta

`.cpdelta` - ZIP-контейнер, созданный средствами JDK. В нём находятся `patch.json` и payload только добавленных или изменённых файлов. При применении целевой список берётся из проверенного `update.json`: совпадающие файлы копируются из установленного дерева, остальные обязаны присутствовать в payload. Файлы, отсутствующие в целевом списке, не переносятся. SHA-256 подтверждает целостность, а не цифровую подпись издателя; доверие к источнику основано на HTTPS и фиксированном репозитории GitHub.

Перед чтением проверяются SHA-256 и размер контейнера. Запрещены абсолютные пути, `..`, пустые сегменты, обратная косая черта, символ NUL, ссылки и регистронезависимые дубликаты. Каждый созданный файл и итоговый хеш дерева проверяются до публикации каталога `Ready`.

## 5. Запуск и загрузка

До интерфейса процесс проверяет журнал установки и готовый каталог. Активной установке передаётся запрос на запуск того же клиента после завершения; готовое обновление планируется в режиме установки с перезапуском. Аргумент с SHA целевой версии предотвращает цикл предстартовой установки.

После открытия интерфейса один фоновый проход:

1. получает `update.json` с уникальным параметром запроса;
2. делает до трёх попыток с тайм-аутом 20 секунд и паузами 1 и 2 секунды;
3. выбирает дельту по номеру, SHA коммита и хешу установленного дерева;
4. при любой ошибке дельты очищает её временные файлы и скачивает полный ZIP;
5. проверяет размеры, SHA-256, каждый файл и дерево;
6. атомарно заменяет прежний `Ready` через временный каталог.

Межпроцессная блокировка не даёт нескольким клиентам одной копии одновременно проверять и скачивать релиз. При закрытии незавершённая `.download` удаляется; следующий запуск начинает загрузку заново.

## 6. Установка после закрытия

Каждый процесс регистрирует в `CashMemory/Updates/processes` PID, время старта и корень установки. При наличии `Ready` первый завершающийся процесс атомарно создаёт `install-journal.json` и скрыто запускает `apply-update.ps1`. Новые процессы, увидев активный журнал, не открывают UI и оставляют запрос на последующий запуск своего клиента.

Помощник ждёт завершения всех зарегистрированных процессов этой копии, удаляет устаревшие регистрации и затем:

1. повторно проверяет подготовленное дерево;
2. переносит управляемые файлы текущей версии в `CashMemory/Updates/Backup`;
3. переносит подготовленную версию на место;
4. проверяет целевой хеш дерева;
5. при ошибке полностью восстанавливает резервную копию;
6. при успехе удаляет `Ready`, резервную копию, журнал и временные файлы.

Обычное закрытие использует режим без перезапуска. Предстартовая установка и запрос, сделанный во время активной установки, запускают тот же `.exe` с безопасными исходными аргументами. Все этапы записываются кодами и временными метками в `update-log.md`.

## 7. Проверки релиза

CI создаёт патчи от двух баз параллельно, применяет каждый к извлечённой базе и сравнивает полный список файлов и хеш дерева с новой сборкой. Отдельные E2E используют локальный JDK HTTP-сервер и две релизные app-image сборки, проверяют три лаунчера, короткую сессию, отсутствие сети, повреждённую дельту, полный fallback, конкурентные клиенты, аварии на фазах замены, Unicode-пути и неизменность `CashMemory`.

## 8. Подготовка реализации и обязательные барьеры

Этот раздел задаёт требования к будущей реализации, не подтверждает её наличие.
03.10.2026 пользователь разрешил реализацию S7 параллельно с S4-S6.
Начало production-кода больше не требует завершённого S6; публичный выпуск
и финальная приёмка по-прежнему требуют общей проверенной матрицы.
Точный контракт параллельной реализации: docs/design/s7-contract-freeze.md.
Существование шаблона отчёта со статусом PENDING или зелёного обычного Maven-профиля
не является разрешением перехода. Автоматическая квитанция S6 имеет статус
`AUTOMATED_ONLY` и отдельно требует независимой проверки.

Порядок интеграции исключает пересекающиеся записи:

1. Зафиксировать точные типы манифеста, байты tree digest, API инвентаризации,
   извлечения и дельты; подготовить независимые тестовые векторы.
2. Параллельно реализовать ядро дельты, локальные HTTP-тесты, установочные
   fault-injection fixtures и договоры публикации в непересекающихся пакетах.
   До наличия API эти задачи готовят fixtures, а не ждут соседнего агента внутри
   занятого параллельного слота.
3. После проверки ядра подключить update-tool, сетевой подготовитель и журнал;
   единственный интегратор меняет общие module-info и Maven reactor.
4. После проверки общего lifecycle подключить три клиента. Они не реализуют
   собственную проверку версий, загрузку, установку или пользовательский UI.
5. Выполнить локальную репетицию трёх версий: две базы и целевую версию. Каждая
   дельта применяется к своей базе и сравнивается с полным целевым деревом.
6. Выполнить независимый аудит и реальную portable update матрицу, затем
   отдельный commit/push и CI. Публичные теги/assets меняет только ведущий
   в разрешённом релизном workflow, не подготовительные агенты.

### 8.1 Требования, которые нельзя заменить облегчённой проверкой

| Проверяемое свойство | Обязательное свидетельство |
| --- | --- |
| Одна проверка при запуске | Счётчик запросов локального JDK HttpServer за длительную сессию; повторные попытки внутри одного прохода учитываются отдельно |
| Два патча | Две разные опубликованные базы, создание и обратное применение обоих контейнеров |
| Отмена загрузки | Настоящий медленный поток, закрытие клиента, отсутствие Ready и частичной загрузки, успешная следующая сессия |
| Полный fallback | Испорченный/неподходящий патч, доказанный запрос полного архива и проверенное целевое дерево |
| Нет установки при живом клиенте | Реальные одновременно работающие разные `.exe`, неизменный исходный managed tree до выхода последнего |
| PID reuse и чужая копия | Отказ считать lease живым только по PID: сравниваются время старта и канонический корень |
| Журнал и откат | Прерывание до/после каждой операции замены, отдельный новый процесс завершает recovery; итог только целая старая либо целая новая версия |
| Перезапуск | После обычного закрытия процесса нет; при предстартовом recovery запущен именно исходный клиент с допустимыми аргументами |
| Пользовательские данные | Список путей и SHA-256 всех данных CashMemory до и после, отдельно исключены только собственные Updates-служебные файлы |
| Безопасность путей | Реальные ZIP с traversal, ADS, reserved names, ссылками, Unicode/case collisions; отказ до записи за пределы staging |
| Невидимость | Статический аудит моделей меню/панели/status и живых дампов всех трёх клиентов; нет кнопки, сообщения или update endpoint |
| Публикация | Mock GitHub операции подтверждают payload-first/update.json-last и отсутствие удаления баз до успешного commit-pointer |

### 8.2 Открытые детали для freeze-фазы S7

Перед первым production-кодом нужно определить единственные, побайтово
проверяемые контракты: порядок сортировки Unicode-путей и кодирование tree
digest; схемы patch.json, lease, restart request и install journal; лимиты
ZIP/JSON и redirects; allowlist аргументов каждого лаунчера; атомарный способ
публикации Ready и восстановления прерванного swap на NTFS.
Они не должны оставаться неявными решениями разных исполнителей.
Их фиксация не меняет одобренные schemaVersion 2, алгоритм tree-delta v1,
две базы, ограничения стека, CashMemory и невидимый жизненный цикл.
